# Karibu — Kenya retail ERP · ongoing implementation after 0.5.0

**A modular ERP designed around a single financial transaction boundary.**

Stack: **Node.js 22+, NestJS 12, TypeScript, PostgreSQL 17, React 18 and Next.js 16.** Functional currency initially KES. This repository contains the full architecture baseline and an implemented, tested accounting kernel; it is **not the finished production ERP**. Read [STATUS.md](STATUS.md) before using it.

## Sandbox sign-in — 0.4.1 recovery

Use **Arena’s Karibu ERP live preview card**, reload, and sign in with your existing credentials. The user confirmed that the earlier partitioned-cookie solution still failed in their actual preview. Its precise external cause is not confirmed; local cookie tests never exercised Arena’s private traffic authorization.

The hosted sandbox now explicitly enables `ENABLE_PREVIEW_MEMORY_SESSION=true`. Successful password login can negotiate a session in **tab memory**, sent in `X-ERP-Session` on same-origin API requests. Cookies are not required. **Reloading requires sign-in again.** Credentials remain unchanged. The session is still hashed, expiring and revocable on the server; CSRF, permission, company and branch checks remain enforced. No token goes in URLs, localStorage, sessionStorage, source or logs.

This is a **development-only tradeoff**, not a production authentication recommendation: JavaScript can access the in-memory credential, unlike an HttpOnly cookie. The feature is off by default and startup refuses it in production. Normal deployments remain HttpOnly-cookie-only. Do not enable permissive CORS or weaken production frame restrictions.

A Chromium cross-site iframe test strips every request/response cookie and verifies accounting and admin access, logout, self-revocation and reload behavior. The separate cookie-only regression also passes. **The user's retry is still needed to confirm the actual Arena/browser environment.** See [recovery design and evidence](docs/08-preview-session-recovery.md).

## What works now

```
Authenticated user A creates a journal source
   → User A submits
   → independent user B approves
   → independent user C posts
   → exact balanced journal + immutable source + audit + outbox
   → General Ledger / trial-balance totals / source drilldown
   → separately approved reversing source, if correction is needed
```

Company membership, branch scope and granular permissions are checked server-side. Posted journals and their lines cannot be updated or deleted. Accounting journal balance is enforced by a deferred PostgreSQL constraint, not merely by the UI. RLS and composite tenant foreign keys protect the schema. Manual postings to control accounts are blocked until matching operational engines exist.

**Not currently working:** real sales/POS, purchasing, customer AR/supplier AP postings and allocations, operational payments/returns/expenses, M-Pesa, tax-register/fiscal posting/eTIMS, stock transfers/counts/reservations/tracking and full operational reconciliations. Initial tax configuration, stock adjustments and customer registration are released only within the bounded development scope above; their parent modules are incomplete. The pure exact-decimal tax kernel now has 11 tests (including 3,000 arithmetic combinations); it is not exposed as a posting API. See the complete gap list in STATUS.

## Native development setup (tested path)

Prerequisites: Node 22+, npm, PostgreSQL 17 with `pgcrypto`, `btree_gist`, `pg_trgm`; Python 3 is only needed to regenerate design artifacts.

1. Create an empty database `erp` owned by a migration-only owner. The owner must be allowed to install the extensions and provision `erp_runtime` (or have a DBA do that explicitly).
2. Copy `.env.example` to `.env`. Set real local owner/runtime URLs and a random runtime password of at least 20 characters. The API receives **only the runtime database role**. Do not use the owner URL for `DATABASE_URL`.
3. Run from repository root:

```sh
npm ci
npm run migrate
npm run seed           # DEVELOPMENT ONLY; creates demo principals/config, not balances
npm run build
```

The seed writes `.runtime/demo.json` and `DEMO_ACCESS.md`. Existing development credentials are not silently reset. If a seeded database remains but the credential file is gone, supply its original `DEMO_PASSWORD` or provision a new disposable development database.

4. In separate terminals:

```sh
npm run dev -w apps/api  # port 3000, bound to 0.0.0.0
npm run dev -w apps/web  # port 5173, same-origin /api proxy
```

Open the web app, sign in as Amina, and select **Karibu Retail / Nairobi**. Create Dr Rent / Cr Utilities with the same value on each side. Submit, sign out, approve as Brian, sign out, post as Carol. The example is a reclassification only, not a cash expense. The auditor is read-only. Own-session revocation/password changes are available under **My sessions**. Inspect source timeline, posted lines and audit trail; request a reversal if appropriate.

No browser requests call localhost for a second service: the browser uses relative `/api/v1` URLs and Next.js proxies them. Development preview host `.e2b.app` is allowed. PostgreSQL is not intended to be publicly accessible.

## Branch administration (0.3)

As Esther, open **Control center → Branches**. Create a unique uppercase code and branch name with a reason. Creation grants nobody access; explicitly assign scopes under Members. Revise names and active state with an expected version; codes/creators never change. A branch with active warehouses or pending unposted sources cannot be deactivated. Historical source attribution remains unchanged and no balance is editable. Felix can review branches but cannot change them. Basic company display-name and warehouse configuration are available in 0.4; new-company onboarding and operational lifecycle management remain unreleased.

## Account controls (0.5)

Open **Control center → Account controls**. Esther (`admin@demo.local`) can propose a new non-control account or a display-name correction. Search and choose an eligible parent heading, or explicitly choose top-level. A submitted proposal has no account/balance effect.

Sign out, then use Felix (`reviewer@demo.local`) to open **Change requests → Pending review**, inspect the proposal and approve or reject it with a reason. The proposer cannot review their own request even if granted both permissions. Approval creates the account or applies the versioned name correction atomically with audit. Amina's journal picker then finds approved postable accounts; the existing three-person journal workflow still applies. These grants are configurable permissions, not role-name checks.

Codes, classification, parent, denomination, active status and original creator cannot be edited through this workflow. Control-account creation/mapping, account closure and broader lifecycle, configurable posting rules remain unreleased; controlled document numbering is now available in the working tree. This is **not** an opening-balance editor or permission to post directly to a control account. See [the contract](docs/09-chart-of-accounts-controls.md) and [browser evidence](docs/browser-coa-result.json).

## Company profile and warehouses (0.4)

As Esther, open **Control center → Company** to view the current company and revise its display name with a reason. The permission is separate from branch management. Tax PIN, code, functional currency, timezone and status stay read-only; changing the display name cannot reclassify existing journals or reassign the legal entity.

Open **Control center → Warehouses** to create a uniquely coded location under an explicitly selected active branch. Parent options and warehouse lists use server-side search/pagination. Warehouse code, parent branch, location type and creator never change. Names and active state use optimistic versions and audited reasons. There is no stock-entry or balance field. Users receive no new access through location creation.

An active warehouse prevents parent-branch deactivation. To close an unused hierarchy, deactivate the warehouse first, then its branch. Reopening requires the branch first. Until operational engines implement safe close checks, **any operational record referencing a warehouse blocks deactivation**, even if that record is inactive/historical or has zero balance. Do not bypass that safeguard with manual balance changes. Direct balance edits and unreleased inventory-domain writes remain denied. Released stock reads are scoped and cost-gated; approved movement insertion is protected by native source/valuation/GL/audit coupling. A restricted database helper exposes warehouse dependency checks.

The organization acceptance test renames/restores the demo company and leaves clearly labeled DEMO location fixtures. It changes no stock or journals. It must not run against a real business tenant.

## Access controls and password recovery (0.2)

Sign in as **Esther** (`admin@demo.local`) to provision members and delegated roles or draft an approval policy. Sign in as **Felix** (`reviewer@demo.local`) to independently publish it. Neither has journal-posting powers. Each member establishes their password through recovery; no administrator is shown an initial password. Membership suspension does not rewrite attribution or revoke unrelated company access.

For local development, configure the following in `.env`:

```ini
RESET_ENCRYPTION_KEY=<64 hex characters generated with: openssl rand -hex 32>
AUTH_MAIL_MODE=file
PUBLIC_WEB_ORIGIN=http://localhost:5173
```

Use the actual trusted HTTPS web origin for a hosted preview; never derive it from user input or the request Host header. Then run **`npm run worker:auth`** from the repository root in another terminal. The API writes an AES-GCM encrypted outbox record; the worker leases a job, writes a private `.runtime/mail/<jobId>.json` development message and marks delivery with a security event. File mode does **not** send email. Local files contain sensitive reset links: never publish them, commit them, or use the file adapter in production. The browser removes the link token from the URL and keeps it only in memory; re-open the original link if the page is reloaded before consumption.

Production mode requires `AUTH_MAIL_MODE=smtp`, a separately held encryption key, an HTTPS `PUBLIC_WEB_ORIGIN`, `SMTP_URL` and `SMTP_FROM`. Start the worker separately, preferably with a dedicated audited worker database role through `AUTH_WORKER_DATABASE_URL` (the current reference falls back to the runtime role). External SMTP delivery, hardened deployment and MFA remain unverified release gates. Missing/reset delivery configuration returns an explicit unavailable response rather than pretending mail was sent. `node scripts/auth-mail-worker.cjs --once` handles one eligible job and exits. Claims use two-minute leases and bounded retries, so delivery is at-least-once; token consumption is single-use.

Legacy pending documents created before migration 004 have no frozen approval contract: their original creator must revise and resubmit before approval/posting. Already posted history remains unchanged. Migrations use checksums and an advisory lock. Existing untracked 001–003 installations require a DBA-verified baseline registration and backup; never automatically mark unknown DDL as applied.

## Tests

```sh
npm test
npx playwright install --with-deps chromium
node scripts/next-production-test.cjs  # after building Next; requires running API
node --test scripts/ops-test.cjs       # isolated local restore drill; operator DB URL required
npm run test:e2e        # requires running API/web and development seed
npm run test:e2e:controls # requires file-mode reset configuration below
npm run test:e2e:branches # branch configuration, no balances
npm run test:e2e:organization # company rename/restore and warehouse hierarchy
npm run test:e2e:preview-memory # live development memory transport enabled; cookies deliberately stripped
npm run test:e2e:coa # maker/reviewer configuration, then three-user posting and trial balance
npm run test:e2e:embedded # requires partitioned cookie mode + OpenSSL; ephemeral local TLS proxy
npm audit
```

The backend tests create a uniquely named disposable database, apply all DDL, seed test-only users, run a real Nest API, and drop the database. Default test owner is the local development `user` with no password, matching this workspace's isolated trust-auth database. For another environment set `TEST_ADMIN_URL` to a disposable cluster's create-database-capable owner and `TEST_RUNTIME_URL` to its preprovisioned `erp_runtime` role (or `TEST_RUNTIME_PASSWORD` for the same host). The test runner substitutes only a uniquely generated test database name; it does not reuse the application database. **Never point test credentials at a production cluster.**

Browser tests deliberately leave DEMO source/journal fixtures in the development database to demonstrate traceability. Backend tests leave no financial fixtures in the preview database. Test evidence reports exact outcomes; browser coverage includes accounting and controls/recovery workflows, not the future full business lifecycle. The controls test leaves demo users/roles and independently published high-value policies; never run it against a real business tenant.

Use independent long URL-safe random `POSTGRES_PASSWORD`, `RUNTIME_DB_PASSWORD` and `AUTH_WORKER_DB_PASSWORD` in `.env`, plus a development-only `DEMO_PASSWORD` if seeding. The Compose database has no published port. The owner secret is provided only to migration/seed, not API.

```sh

# Optional after configuring recovery variables and trusted web origin:
docker compose --profile auth up -d auth-worker
```

The default Compose file is development/reference. A separate `docker-compose.prod.yml`, non-root multi-stage images and Ubuntu operator scripts are now provided, but Docker execution is not verified in this sandbox. Image digest pinning/scanning, live ingress, external SMTP and host recovery/reboot drills remain gates. Set `COOKIE_SECURE=true` behind TLS. Configure trusted proxy IP handling explicitly before relying on IP-based security events; the current native API intentionally does not trust arbitrary forwarded-IP headers.

## Financial and compliance boundaries

No live tax rules are seeded, no tax-compliance certification is claimed, and no provider secrets/credentials are included. KRA tax/eTIMS design references are in the architecture. Provider acceptance, merchant verification, full lifecycle tests, control reconciliations, accountant sign-off and production security review remain mandatory. “Zero reported npm vulnerabilities” is a dependency snapshot, not evidence of complete security.

Continue customer credit/exposure and AR contracts, then supplier/AP and procurement dependencies, while retaining the remaining master/security/organization lifecycle and production gates. Never substitute disconnected CRUD for atomic source/ledger workflows.
